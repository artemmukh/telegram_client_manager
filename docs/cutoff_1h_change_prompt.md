# Промпт: изменить окно отмены/переноса записи с 2 часов на 1 час

Готовый промпт для мультиагентного workflow проекта
(`.claude/agents/workflow.md`: planner → researcher → implementer →
routine → verifier → reviewer). Скопируй раздел "Задача для агента".

---

## Контекст проблемы (как описал заказчик)

Клиенту приходит напоминание за 2 часа до записи с кнопками
"✅ Приду" / "❌ Не приду". Но правило отмены запрещает отменять запись
менее чем за 2 часа до приёма (`CANCELLATION_CUTOFF_HOURS = 2`). На
практике к моменту, когда 2ч-напоминание доходит до клиента, окно для
отмены уже закрывается или закрыто — кнопка "Не приду" почти
бессмысленна. Нужно сдвинуть окно отмены/переноса на **1 час до
приёма**, чтобы между 2ч-напоминанием и запретом на отмену оставался
реальный запас времени, и чтобы вся логика, тексты предупреждений/алертов
и (где применимо) данные в БД были согласованы с новым правилом.

### Важная находка, которую нужно перепроверить и явно решить

При исследовании код-базы обнаружено, что кнопка "❌ Не приду",
присланная именно в 2ч-напоминании, ведёт в
`bot/handlers/client/appointment_response.py:handle_cancel_confirmation_yes`,
который вызывает
`cancel_appointment_by_client(..., enforce_cutoff=False)` — то есть
**cutoff уже не проверяется** для отмены через кнопку в напоминании
(с комментарием в коде "2h cutoff does not apply to the
reminder-triggered flow"). Cutoff проверяется (`enforce_cutoff=True`)
только при отмене через раздел "Мои записи"
(`appointment_manage_*` / `appointment_history_*` хендлеры в том же
файле).

Это значит, что до сих пор отмена именно по кнопке из напоминания уже
не блокировалась вообще (в любой момент, хоть за минуту до приёма), а
блокировалась только отмена через общий раздел управления записями.
**Планировщик (planner) должен явно зафиксировать в плане, как это
трактовать**, и вынести решение на подтверждение перед реализацией:

- Вариант А (по умолчанию, минимальное изменение): оставить
  `enforce_cutoff=False` в reminder-flow как есть (не в скоупе задачи),
  просто заменить сам порог `CANCELLATION_CUTOFF_HOURS` с 2 на 1 везде,
  где он используется с `enforce_cutoff=True` (общий раздел управления
  записями, перенос/reschedule).
- Вариант Б: раз уж приводим окно к единому знаменателю — сделать
  cutoff=1ч действующим и для отмены из напоминания тоже (убрать
  `enforce_cutoff=False` там), чтобы поведение было одинаковым
  независимо от того, откуда клиент отменяет.

Если из переписки с заказчиком неясно, какой вариант нужен — **planner
обязан переспросить перед implementer**, а не выбирать сам. Не додумывай
это за пользователя.

## Задача для агента

### 1. Код (бизнес-логика)

- `bot/services/appointment/appointment_management.py`:
  - `CANCELLATION_CUTOFF_HOURS = 2` → `1`. Эта константа используется
    и для отмены (`_is_within_cancellation_cutoff`), и для проверки
    минимального интервала при переносе
    (`_is_new_datetime_within_cutoff` / `request_reschedule_by_client`)
    — оба места должны измениться синхронно, это одна константа.
  - По итогам решения из раздела "важная находка" — при необходимости
    поправить `enforce_cutoff` вызовы в
    `bot/handlers/client/appointment_response.py`.
- **НЕ трогать** расписание самих напоминаний
  (`timedelta(hours=24)` / `timedelta(hours=2)` в
  `bot/services/appointment/appointment_scheduler.py`, job id вида
  `appt_{id}_2h`, пресеты `bot/keyboards/client/reminder_kb.py`
  ("🔔 За 24ч и за 2ч" и т.п.) — это про то, КОГДА присылается
  напоминание, отдельное понятие от окна отмены/переноса. Смешивать их
  не нужно, если явно не решено обратное.

### 2. Тексты предупреждений/алертов (обязательно найти все вхождения)

Найди и обнови все места, где формулировка ссылается на "2 часа" в
контексте отмены/переноса (используй `grep -rn "2 час" bot/` как
отправную точку, дальше проверь семантику каждого совпадения — среди
находок есть посторонние "через 2 часа" в примерах парсинга даты,
которые трогать не нужно):

- `bot/exceptions/appointment_exceptions.py` — docstring
  `CancellationWindowExpiredError`: "Отмена записи менее чем за 2 часа
  до приёма." → 1 час.
- `bot/services/appointment/appointment_management.py`:
  - `"Отмена возможна не позднее чем за 2 часа, свяжитесь с клиникой"`
  - `"Новое время должно быть не менее чем через 2 часа от текущего
    момента, свяжитесь с клиникой."`
- Любые другие пользовательские сообщения/alert'ы (`show_alert=True` и
  т.п.), справочные тексты в хендлерах или клавиатурах, где упоминается
  двухчасовое окно отмены/переноса.

### 3. Документация, созданная ранее в этом проекте

- `docs/manual_qa_checklist.md` — есть минимум 3 места с "за 2 часа"
  применительно к отмене/переносу (строки ~185, ~243, ~309 на момент
  написания этого промпта) — обновить на 1 час, включая сценарии
  "дождаться момента ровно за N часов".
- `docs/e2e_test_prompt.md` / `tests/test_e2e_full_flow.py` (уже
  реализован по прошлому промпту) — проверить, нет ли там захардкоженных
  2-часовых допущений о cutoff, поправить при необходимости.

### 4. Тесты

- `tests/test_appointment_management.py` содержит явные тесты на
  cutoff, включая `test_cancel_appointment_by_client_blocked_within_2h_when_cutoff_enforced`
  и тест на reschedule-cutoff (`test_request_reschedule_by_client_raises_when_new_time_within_cutoff`).
  Переименуй/обнови их под 1 час, не создавая дублирующих тестов.
- Обязательно покрой граничные случаи для нового порога: чуть меньше
  1 часа (блокируется), ровно 1 час, чуть больше 1 часа (разрешено) —
  по аналогии с тем, как были покрыты границы для 2 часов.
- Если реализован Вариант Б из "важной находки" — добавь тест,
  что отмена из reminder-flow теперь тоже блокируется в пределах 1ч.
  Если оставлен Вариант А — оставь существующий тест
  `test_cancel_appointment_by_client_bypasses_cutoff_when_disabled` как
  документирующий текущее (осознанно неизменное) поведение.

### Порядок выполнения (обязателен по workflow.md)

1. **planner** — фиксирует scope, явно проговаривает решение по
   "важной находке" (Вариант А/Б), список файлов и рисков.
2. **researcher** — находит все места использования
   `CANCELLATION_CUTOFF_HOURS`, `enforce_cutoff`, все текстовые
   вхождения "2 час" в контексте отмены/переноса и связанные тесты
   (список выше — стартовая точка, не исчерпывающий).
3. **implementer** — вносит изменения в код и тексты.
4. **test-expert** — обновляет/добавляет тесты на граничные случаи,
   прогоняет `pytest`.
5. **reviewer** — сверяет с CLAUDE.md (SQL только в репозиториях,
   бизнес-правила только в Service, никакой логики в хендлерах) и
   проверяет, что все найденные текстовые упоминания приведены к
   единому значению (1 час) без расхождений между кодом, алертами и
   документацией.

### Definition of Done

- Единственная константа `CANCELLATION_CUTOFF_HOURS = 1` управляет и
  отменой, и минимальным интервалом переноса.
- Все пользовательские тексты про окно отмены/переноса говорят про
  1 час, без расхождений.
- Явно задокументировано (в PR-описании/выводе planner), как решена
  "важная находка" про `enforce_cutoff=False` в reminder-flow.
- `pytest` зелёный, включая новые/переименованные граничные тесты.
- `docs/manual_qa_checklist.md` обновлён и не противоречит новому
  поведению.
