Готовый промпт для мультиагентного workflow проекта
(`.claude/agents/workflow.md`: planner → researcher → implementer →
routine → verifier → reviewer). Скопируй раздел "Задача для агента".

`docs/zombie_pending_fix_prompt.md`, `docs/slot_conflict_detection_prompt.md`,

## Контекст проблемы

В "Обзоре записей" админ сейчас видит **все** записи в базе — нет
фильтрации ни по клинике, ни по врачу. Ни `AppointmentPaginationService`,
ни `AppointmentRepository`-методы, которые её обслуживают, не принимают
`clinic_id`/`doctor_id` вообще.

Специфика заказчика: сейчас в клинике 2 врача, каждый сам ведёт свою
запись через бота — отдельной роли "админ" нет, врач и есть админ своего
расписания. Но у других клиник (будущих клиентов бота) может быть
отдельный ресепшн-админ, управляющий несколькими врачами и обязанный
видеть все их записи разом. Нужна гибридная модель, а не жёсткий выбор
одного из двух вариантов.

## Согласованная модель (обсуждена и зафиксирована с пользователем)

Найдено при ресерче: отдельной таблицы-связки "админ ↔ врач" заводить не
нужно — `appointments.admin_id` (поле `Appointment.doctor_id` в модели)
уже однозначно указывает на врача-исполнителя что при self-booking
клиента, что при создании записи админом (админ, создающий запись,
действует как врач на своём же расписании — `admin_id` совпадает с ID
самого создающего админа).

Схема:

- Новое nullable-поле `users.visibility_scope: str | None`, значения
  `'own'` / `'clinic'`.
- `NULL` или `'own'` → админ видит только записи, где `admin_id` равен
  его собственному `User.ID` (это его собственное расписание, независимо
  от того, кто создал запись — сам врач или клиент через self-booking на
  этого врача).
- `'clinic'` → админ видит все записи по своему `clinic_id`, независимо
  от врача (сценарий отдельного ресепшн-админа).
- **Дефолт `'own'` подтверждён пользователем как окончательный** для
  текущих 2 врачей: они сейчас видят записи друг друга только как
  побочный эффект отсутствия фильтрации (бага), не пользуются этим
  намеренно — можно просто убрать без риска сломать рабочий процесс.

## Задача для агента

### 1. Модель и Repository — новое поле

- `bot/models/user.py` — добавить `visibility_scope: str | None = None`.
- `bot/repositories/user_repository.py` — прочитать/сохранить
  `visibility_scope`; миграция `ALTER TABLE ... ADD COLUMN` по уже
  существующему в проекте паттерну try/except (см. как это уже сделано
  для других добавленных колонок в `appointment_repository.py`/
  `staff_repository.py`).

### 2. Service — метод разрешения фильтра

Новый метод в `bot/services/appointment/appointment_management.py`:

```python
async def resolve_admin_appointment_filter(admin_telegram_id: int) -> tuple[int, int | None]:
    """Returns (clinic_id, doctor_id_or_none)."""
```

- `clinic_id` — через уже существующий `get_admin_clinic(...)`.
- Смотрит `visibility_scope` у самого админа (его `User`-запись):
  - `None`/`'own'` → возвращает `(clinic_id, admin_user.ID)`;
  - `'clinic'` → возвращает `(clinic_id, None)`.

### 3. Repository — фильтрация по clinic_id/doctor_id ВЕЗДЕ, не только в списке

Критически важно: пробросить `clinic_id` (всегда) и опциональный
`doctor_id` (применяется только если не `None`) во **все** методы выборки
записей для админа в `appointment_repository.py`, а не только в
основной вкладке списка:

- `get_appointments_page` / `count_appointments`
- `get_appointments_by_status_page` / `count_appointments_by_status`
- `get_appointments_by_name` / `get_appointments_by_name_page` (поиск по
  имени)
- `get_appointments_by_client_id` / `get_appointments_by_client_id_page`
  (поиск по телефону/клиенту)

Если поправить только "список/все статусы" и забыть про поиск по
имени/телефону — врач с `visibility_scope='own'` сможет обойти
ограничение, просто найдя нужного клиента по имени или телефону. Это
не отдельная фича, это часть того же самого фикса — закрывать в одном
изменении, не откладывать.

### 4. Service — прокинуть фильтр через пагинацию

`bot/services/appointment/appointment_pagination_service.py` —
`paginate_all_appointments_by_tab` и `paginate_appointments` (все режимы:
`mode="list"`/`"search"`/`"phone"`) должны принимать и прокидывать
`clinic_id`/`doctor_id` дальше в repository. **Не трогать**
`paginate_client_appointments`/`paginate_active_client_appointments` —
это клиентские методы, уже отдельно скоуплены по `telegram_id`, к этой
задаче не относятся.

### 5. Handler — резолвить фильтр один раз на каждую точку входа

`bot/handlers/admin/appointment_management/appointment_browser.py` —
вызвать `resolve_admin_appointment_filter` один раз в каждой точке входа
(`browse_appointments`, `search_all`, `approve_search`, `paginate`) и
передать результат во все вызовы `pagination_service` в этой точке входа.

### 6. Клавиатура выбора врача для записи не должна показывать `'clinic'`-scope админов

Найдено при ресерче: клавиатура выбора специалиста для self-booking
генерируется единственным методом —
`AppointmentManagement.list_bookable_staff()`
(`bot/services/appointment/appointment_management.py:71`), используется
только в `bot/handlers/client/appointment_booking.py:58`. Больше нигде в
проекте отдельного экрана "выбрать врача" нет — когда запись создаёт
админ, врачом автоматически становится он сам (`doctor_telegram_id` = его
собственный telegram id).

Правило: если у админа `visibility_scope == 'clinic'` — он ресепшн/
управляющий, а не врач, и не должен появляться в списке специалистов, к
которым можно записаться. Отфильтровать это нужно **только внутри
`list_bookable_staff`** (например, убрать из результата
`get_staff_users_by_clinic_id` записи с `visibility_scope == 'clinic'`
перед возвратом) — **не трогать** сам `get_staff_users_by_clinic_id` в
`user_repository.py`, потому что тот же метод используется для рассылки
уведомлений всем админам клиники
(`bot/services/client/client_notifications.py:30,59`) — там
`'clinic'`-scope админ как раз обязан оставаться в списке получателей,
это не тот же самый список, что и "выбери врача".

### 7. Провижининг (не код, а операционный шаг) — ручная установка `'clinic'` без скрипта

Назначение нового ресепшн-админа с `'clinic'` — это разовая ручная
установка одного значения в БД, скрипт для этого не нужен. Пользователь
уже сейчас планирует применить это на практике: 2 врача (Руста и Елена)
остаются `'own'` (дефолт, ничего трогать не нужно, `NULL` уже значит
`'own'`), а Артём (управляющий клиникой) должен получить `'clinic'`.

**Подтверждено пользователем (закрывает прежнюю нестыковку с ID):**
Артём — это `685889801` из уже захардкоженных id в
`staff_repository.py:30` (не "658", это было неточное указание префикса
в разговоре). Он уже есть в таблице `staff` для резолва клиники, просто
ещё не проходил регистрацию как `User` в боте. Два других id в том же
файле (`226655040`, `37470594`) — Руста и Елена, врачи, остаются
`'own'`. Добавлять Артёма в `staff`-таблицу не нужно — он там уже есть.

**Обновление (после переноса `visibility_scope` из `users` в `staff`):**
поле `visibility_scope` теперь живёт в таблице `staff`, а не в `users`.
Это хорошая новость, а не потеря функциональности — Артём уже есть в
`staff` (для резолва клиники), поэтому ждать его регистрации как `User`
через бота больше не нужно. Значение можно проставить сразу же, в любой
момент.

**Как пользователь может сделать это сам через DB Browser for SQLite**
(бесплатная GUI-программа, отдельно от кода — да, это возможно и не
требует навыков SQL):

1. Установить [DB Browser for SQLite](https://sqlitebrowser.org/) (если
   ещё не установлен).
2. **Остановить бота** перед редактированием (или убедиться, что в этот
   момент нет активной записи в БД) — SQLite позволяет только одному
   процессу писать в файл одновременно; редактирование "на живую" рядом
   с работающим ботом рискует конфликтом блокировки файла.
3. Открыть в DB Browser тот файл БД, что указан в `.env` в переменной
   `DATA_BASE` (это основная БД бота — **не** `data/reminders.db`, там
   лежат только job'ы планировщика, а не пользователи).
4. Вкладка **"Browse Data"** (Просмотр данных) → выбрать таблицу
   `staff`.
5. Найти нужную строку по колонке `telegram_user_id = 685889801`
   (Артём — он уже есть в этой таблице).
6. Кликнуть в ячейку колонки `visibility_scope` этой строки, ввести
   `clinic` (без кавычек, в нижнем регистре — именно так это значение
   ожидает код).
7. Нажать **"Write Changes"** (иконка дискеты в верхней панели) — без
   этого шага изменения останутся только в памяти программы и не
   попадут в файл на диске.
8. Запустить бота обратно.

Колонка `visibility_scope` появится в таблице `staff` только после того,
как миграция отработает при старте бота (`StaffRepository.init()`) — до
этого в таблице `staff` такой колонки ещё нет.

### 8. Обязательно проверить перед реализацией (не предполагать)

- Есть ли в реальных данных записи с `admin_id IS NULL` (например,
  созданные до назначения врача)? При `'own'`-скоупинге такие записи
  станут невидимы вообще ни для одного `'own'`-админа. Если такие записи
  есть — **остановиться и спросить пользователя**, как их показывать.
- Распределение id из `staff_repository.py` подтверждено пользователем:
  `685889801` = Артём → `'clinic'`; `226655040` и `37470594` = Руста и
  Елена → `'own'` (дефолт, менять не нужно). Это уже не открытый вопрос,
  но при реализации всё равно свериться, что в `users` для двух врачей
  действительно те же telegram_id, что и в `staff`.

## Порядок выполнения (обязателен по workflow.md)

1. **planner** — фиксирует scope по разделу "Согласованная модель";
   явно включает пункт 8 ("обязательно проверить") как шаг, который
   выполняется до/во время реализации, не после.
2. **researcher** — перепроверяет актуальный список repository/service
   методов, которые обслуживают "Обзор записей" (могли измениться с
   момента ресерча), проверяет реальные данные на `admin_id IS NULL`,
   перечисляет все три (или сколько сейчас есть) telegram-id из
   `staff_repository.py`. **Если найдётся расхождение с ожиданиями —
   см. правило в начале документа: сообщить и ждать решения.**
3. **database-expert** — проверяет миграцию нового поля и корректность
   SQL-фильтрации по `clinic_id`/`admin_id` во всех перечисленных
   методах.
4. **implementer** — реализует модель, Service-метод, repository-фильтры,
   прокидку через pagination service, handler.
5. **test-expert** — тесты: `'own'`-админ не видит чужие записи ни в
   списке, ни в поиске по имени/телефону; `'clinic'`-админ видит все
   записи своей клиники; запись из чужой клиники не видна ни при каком
   scope.
6. **reviewer** — сверяет с CLAUDE.md (фильтрация — бизнес-правило,
   должно жить в Service/Repository, не в хендлере), проверяет, что
   **все** точки поиска (список/имя/телефон) действительно защищены, а
   не только основная вкладка.

## Definition of Done

- Админ с `visibility_scope` `NULL`/`'own'` видит во всех трёх точках
  входа (список/все статусы, поиск по имени, поиск по телефону) только
  записи, где `admin_id` равен его собственному `User.ID`.
- Админ с `'clinic'` видит все записи своей клиники по всем трём точкам
  входа, независимо от врача.
- Записи чужой клиники не видны ни при каком scope.
- `'clinic'`-scope админ не появляется в клавиатуре выбора врача при
  self-booking (`list_bookable_staff`), но по-прежнему получает рассылки
  уведомлений всем админам клиники (`get_staff_users_by_clinic_id` не
  тронут).
- Факты по пункту 8 ("обязательно проверить") подтверждены реальными
  данными, а не предположены; при расхождении — решение получено от
  пользователя до выкатки.
- `pytest` зелёный.
