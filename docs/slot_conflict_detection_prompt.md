# Промпт: проверка занятости слота (conflict detection) при записи на приём

Готовый промпт для мультиагентного workflow проекта
(`.claude/agents/workflow.md`: planner → researcher → implementer →
routine → verifier → reviewer). Скопируй раздел "Задача для агента".

Это пункт **2 из 4** согласованного плана (остальные —
`docs/zombie_pending_fix_prompt.md`,
`docs/booking_requests_resync_refactor_prompt.md`,
`docs/admin_visibility_scope_prompt.md`). Независим от остальных трёх по
коду.

---

## ⚠️ Обязательное правило для всех агентов (в первую очередь researcher)

Если в процессе исследования или реализации обнаруживается **костыль,
несоответствие, дубликат логики, неочевидный edge-кейс или коллизия**
(например: ещё одно место генерации слотов, о котором не знаем; функция
проверки занятости, дублирующая новую; расхождение в том, как статусы
хранятся в БД) — **агент обязан сразу сообщить об этом текстом и
остановиться**, дождавшись решения пользователя. Не додумывать, не
выбирать "разумный" вариант самостоятельно.

## Контекст проблемы

Сейчас в проекте **нигде нет проверки занятости слота** — ни при
самозаписи клиента, ни при создании записи админом, ни при подтверждении
переговоров. `generate_available_slots`
(`bot/handlers/utils/client_utils/booking_helpers.py:41`) прямо в
докстринге говорит: "No availability/conflict checking" — выдаёт полный
список слотов по расписанию, не проверяя, заняты ли они. Два клиента (или
клиент и админ) могут получить запись на одно и то же время к одному
врачу без единого предупреждения.

## Согласованное правило (обсуждено и зафиксировано с пользователем)

**Блокирует слот только статус `CONFIRMED`.** `PENDING`-заявки слот
**не блокируют** и не резервируют его. Если несколько клиентов независимо
оказались в PENDING на одно и то же время у одного врача — это не
ошибочное состояние и не требует автоматического разрешения конфликта:
когда админ подтверждает одну из заявок, вторую он **вручную** отклоняет
или предлагает по ней другое время — стандартными уже существующими
механизмами переговоров, без новой логики авторазрешения конфликтов.

## Уже проведённый ресерч — используй эти факты, не переоткрывай

- Единственный генератор слотов на весь проект — `generate_available_slots`
  (`bot/handlers/utils/client_utils/booking_helpers.py:41`). Используется
  ровно в двух местах: self-booking клиента
  (`bot/handlers/client/appointment_booking.py:134`) и клиентский
  reschedule (`bot/handlers/client/appointment_reschedule.py:154`).
  Дублирующей реализации нет.
- Админские флоу (`bot/handlers/admin/appointment_management/appointment_creation.py`,
  `booking_requests.py` propose-действие, `reschedule_requests.py`
  propose-действие) **вообще не показывают список слотов** — дата/время
  вводятся свободным текстом через `parse_ru_datetime`/
  `datetime_processing`. Патчить там нечего — единственная защита для
  всей админской стороны — commit-time проверка (см. пункт 3 ниже).
- В `bot/repositories/appointment_repository.py` нет метода "записи
  врача на дату" — нужно добавить новый, по образцу
  `get_appointments_by_client_id` (строка 155).
- Схемные нюансы, обязательные к учёту при написании нового метода:
  - В SQL колонка врача называется **`admin_id`**, а в модели
    `Appointment` это поле называется **`doctor_id`**
    (маппинг в `_row_to_appointment`, строка ~469). Фильтровать в SQL
    нужно по `admin_id`, результат мапится в `doctor_id`.
  - `datetime` хранится как **TEXT** в формате `"YYYY-MM-DD HH:MM"`, не
    нативный тип даты — фильтрация по дню через `LIKE 'YYYY-MM-DD%'`
    или сравнение строк, не через сравнение дат.
  - Индекса на `admin_id` нет (есть только
    `idx_appointments_clinic_datetime` на `clinic_id, datetime`) — новый
    запрос "врач+дата" без индекса будет полным сканом таблицы; решить,
    нужен ли новый индекс, на этапе реализации.
  - `AppointmentStatus.CONFIRMED`/`PENDING` хранятся как строки
    `'confirmed'`/`'pending'` (`.value` из
    `bot/utils/appointment_enums.py`).

## Задача для агента

### 1. Repository

Добавить `get_appointments_by_doctor_and_date(doctor_id: int, date: str) -> list[Appointment]`
в `appointment_repository.py`, фильтруя `WHERE admin_id = ? AND datetime
LIKE ? AND status = 'confirmed'`. Возвращать доменные модели
`Appointment`, не сырые строки (см. CLAUDE.md — репозитории никогда не
возвращают tuple/dict/sqlite-row).

### 2. Service — фильтрация слотов на показе

Новый метод в `bot/services/appointment/appointment_management.py`,
например `get_available_slots(doctor_id, day, now)`: вызывает уже
существующий чистый `generate_available_slots(day, now)`, затем убирает
из результата слоты, совпадающие по datetime с записями из
`get_appointments_by_doctor_and_date(doctor_id, day)` (только
`CONFIRMED`). Обновить оба клиентских колл-сайта
(`appointment_booking.py:134`, `appointment_reschedule.py:154`), чтобы
использовали этот новый Service-метод вместо прямого вызова
`generate_available_slots`.

### 3. Commit-time defense-in-depth (обязательная защита, а не бонус)

Добавить проверку занятости слота в момент, когда datetime фактически
фиксируется как `CONFIRMED`:

- `AppointmentManagement.create_appointment` (админ создаёт запись — это
  **единственная** защита для этого флоу, т.к. там нет списка слотов);
- `propose_new_datetime` (и клиентские, и админские вызовы — тоже
  единственная защита для admin-propose флоу, см. ресерч выше);
- `confirm_pending_request` (админ подтверждает PENDING-заявку клиента —
  критично, поскольку PENDING не резервирует слот, и к моменту
  подтверждения слот мог уже быть занят другой, ранее подтверждённой
  записью).

Завести новое доменное исключение (например `SlotUnavailableError` в
`bot/exceptions/appointment_exceptions.py`), поднимать его при коллизии.
Хендлеры ловят его и показывают пользователю понятное сообщение ("это
время уже занято, выберите другое" / админу — явное предупреждение о
конфликте, дальше он решает вручную: отклонить или предложить другой
слот второй стороне).

### 4. Тесты

- Repository: тест на `get_appointments_by_doctor_and_date` — только
  `CONFIRMED` возвращается, `PENDING`/`CANCELLED`/`EXPIRED` не мешают.
- Service: тест, что занятый CONFIRMED-слот пропадает из
  `get_available_slots`, а PENDING-заявка на то же время слот не
  скрывает.
- Тест на гонку: два независимых PENDING на одно время у одного врача —
  оба создаются успешно (PENDING не блокирует); при попытке подтвердить
  второй, когда первый уже CONFIRMED на тот же слот — поднимается
  `SlotUnavailableError`.
- Тест на `create_appointment`/`propose_new_datetime` — конфликт с уже
  существующей CONFIRMED записью того же врача на тот же datetime
  поднимает исключение, а не создаёт дубликат молча.

## Порядок выполнения (обязателен по workflow.md)

1. **planner** — фиксирует scope по разделу "Согласованное правило" и
   "Уже проведённый ресерч" выше; уточняет, нужен ли новый индекс на
   `admin_id` сразу или можно отложить (учитывая объём таблицы).
2. **researcher** — перепроверяет актуальность фактов из раздела
   "Уже проведённый ресерч" (могли устареть), ищет любые другие места,
   которые могли появиться с момента ресерча и показывают время/слоты
   пользователю. **Если найдётся что-то новое/расходящееся — см. правило
   в начале документа.**
3. **implementer** — реализует repository-метод, Service-обёртку,
   commit-time проверки, доменное исключение.
4. **database-expert** — проверяет SQL-запрос (в т.ч. `LIKE`-фильтр по
   TEXT-дате, потенциальный индекс) на корректность и производительность.
5. **test-expert** — пишет тесты из пункта 4, прогоняет `pytest`.
6. **reviewer** — сверяет с CLAUDE.md (SQL только в репозитории,
   бизнес-правило "что считается занятым" только в Service, никакой
   логики в хендлерах кроме перехвата исключения и показа сообщения).

## Definition of Done

- Слот с существующей CONFIRMED-записью у врача никогда не показывается
  как свободный ни в одном из клиентских флоу.
- Создание/подтверждение/предложение времени, конфликтующее с уже
  CONFIRMED записью на тот же врач+datetime, поднимает
  `SlotUnavailableError` и не создаёт тихого дубля.
- PENDING-заявки слот не блокируют — несколько параллельных PENDING на
  одно время это ожидаемое, а не ошибочное состояние.
- `pytest` зелёный, включая новые тесты на гонку/конфликт.
