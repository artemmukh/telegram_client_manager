# Промпт: глобальные E2E-тесты бота (реальный usage flow, реальная БД)

Этот файл — готовый промпт для запуска через мультиагентный workflow
проекта (`.claude/agents/workflow.md`: planner → researcher → implementer
→ routine → verifier → reviewer, либо вручную test-expert). Скопируй
содержимое раздела "Задача для агента" и передай его агенту/сессии.

---

## Задача для агента

Спроектируй и реализуй набор **глобальных end-to-end тестов** для
Medical Appointment Telegram Bot, проверяющих реальный usage flow
через все архитектурные слои (`Handler → Service → Repository → DB`)
на **реальной SQLite базе** (файл на диске через `tmp_path`, как в
`tests/test_user_repository.py` и `tests/test_appointment_repository.py`
— НЕ in-memory, НЕ моки репозиториев). Работа состоит из двух частей.

### Часть 1 — Автоматизированные pytest E2E-тесты

Создай `tests/test_e2e_full_flow.py` (или несколько файлов
`tests/e2e/test_*.py`, если так удобнее по объёму — следуй структуре
`tests/`).

Требования:

- Используй `pytest_asyncio.fixture` с `tmp_path`, поднимающий реальные
  `UserRepository`, `AppointmentRepository`, `ClinicRepository`,
  `StaffRepository` на одном и том же файле SQLite (см. `repo.init()`
  паттерн в `tests/test_user_repository.py`).
- Не мокай репозитории. Мокай/фейкай только внешние границы, которые
  реально нельзя тестировать локально — Telegram Bot API
  (`aiogram.Bot.send_message` и т.п.) и системные часы, если нужно.
  Существующие `Fake*Repository` из `tests/conftest.py` здесь **не
  используются** — это тесты слоя изоляции сервисов, а нужен реальный
  сквозной прогон через настоящую БД.
- Собери сценарии в один непрерывный flow (создание клиники → создание
  клиента/регистрация → создание приёма → изменение статуса → перенос →
  отмена/завершение → напоминание) плюс отдельные тесты на граничные
  случаи внутри каждого шага.
- Тестовые данные придумай сам, реалистичные и на русском (имена,
  телефоны в формате `+998...`, названия клиник, услуги) — не
  согласовывай конкретные значения, только держись существующих
  доменных моделей (`bot/models/user.py`, `bot/models/appointment.py`,
  `bot/models/clinic.py`, `bot/models/staff.py`) и enum'ов
  (`bot/utils/appointment_enums.py`, `bot/utils/role.py`).
- Проверяй итоговое состояние БД через сами репозитории (`get_*`
  методы), а не через внутренние приватные поля.
- Обязательно покрой сценарии из области видимости ниже.

### Часть 2 — Ручной QA-сценарий (чек-лист)

Создай `docs/manual_qa_checklist.md` — пошаговый чек-лист на русском
для человека, который вручную гоняет бота в Telegram с реально
заполненной БД (dev-инстанс, не продакшен). Формат: пронумерованные
шаги вида "Действие → Ожидаемый результат", сгруппированные по тем же
сценариям, что и в Части 1. Отдельно вынеси блок подготовки данных
(что и в каком порядке завести через админ-панель/БД перед прогоном),
и блок с ожидаемыми Telegram-сообщениями/клавиатурами на каждом шаге.

### Область видимости (обязательные сценарии)

1. **Регистрация клиента** — `/start` → ввод телефона/имени → привязка
   к существующему пациенту в БД по номеру телефона → повторный
   `/start` уже зарегистрированным пользователем (идемпотентность).
2. **Админ: управление клиентами** — создание клиента, поиск (по имени
   и телефону), редактирование (включая запрос смены имени и его
   подтверждение/отклонение — `name_change_approval.py`), удаление,
   проверка что все изменения видны через `client_browser`.
3. **Записи на приём** — создание приёма админом, booking request от
   клиента и его подтверждение/отклонение админом, перенос
   (`reschedule`) с обеих сторон, отмена, завершение
   (`appointment_completion`), проверка пагинации в
   `appointment_pagination_service`.
4. **Уведомления и напоминания** — постановка задач в
   `appointment_scheduler`/`appointment_jobs`, срабатывание напоминаний
   за 24ч/2ч, авто-завершение приёма и follow-up admin-промпт (см.
   `test_phase4_integration.py` как референс поведения), отмена
   напоминаний при отмене/удалении приёма.

### Референсы в проекте (обязательно изучи перед написанием)

- `tests/conftest.py` — паттерн фейков для юнит-тестов сервисов
  (не переиспользуется в E2E, но покажет доменные модели).
- `tests/test_user_repository.py`, `tests/test_appointment_repository.py`
  — эталонный паттерн реальной SQLite через `tmp_path`.
- `tests/test_phase2_integration.py`, `test_phase3_integration.py`,
  `test_phase4_integration.py` — существующие интеграционные сценарии,
  не дублируй их, расширяй/связывай в сквозной flow.
- `bot/services/appointment/*`, `bot/services/client/*` — бизнес-логика,
  которую должен вызывать тест (через сервисы, не мимо них).
- `CLAUDE.md` и `.claude/agents/workflow.md` — архитектурные правила
  проекта (Handler→Service→Repository→DB, никаких SQL вне репозиториев
  и т.д.) — тесты не должны их нарушать и должны это обеспечивать.

### Правила (из CLAUDE.md, обязательны)

- Не дублируй существующие фикстуры/хелперы — расширяй при необходимости.
- Не создавай новых абстракций без необходимости.
- Минимальные, предсказуемые изменения, консистентные со стилем проекта.
- Заверши работу прогоном `pytest` и покажи, что всё зелёное.

### Порядок выполнения (обязателен по workflow.md)

1. **researcher** — находит все нужные модели/сервисы/существующие тесты
   выше и уточняет сигнатуры репозиториев/сервисов.
2. **implementer** — пишет `tests/test_e2e_full_flow.py` и
   `docs/manual_qa_checklist.md`.
3. **test-expert** — прогоняет и стабилизирует тесты, проверяет
   отсутствие flaky-моментов (особенно вокруг `AsyncIOScheduler` и
   времени).
4. **reviewer** — сверяет с чек-листом из CLAUDE.md (никакого SQL вне
   репозиториев, никакой бизнес-логики в хендлерах и т.п.) и с тем, что
   тесты реально идут через реальную БД, а не через моки.

### Definition of Done

- `pytest tests/test_e2e_full_flow.py -v` зелёный, база реальная SQLite
  на каждый тест/модуль (через `tmp_path`), без падений и без флейков
  при повторном запуске.
- `docs/manual_qa_checklist.md` создан и покрывает все 4 сценария из
  области видимости.
- Никаких моков репозиториев внутри E2E-теста.
- Все проверки идут через публичные методы репозиториев/сервисов.
