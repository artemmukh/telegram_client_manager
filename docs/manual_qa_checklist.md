# Ручной QA-чек-лист: полный usage flow бота

Пошаговый чек-лист для ручного тестирования бота в Telegram на
dev-инстансе (реальная БД `data/data_base.db`, НЕ продакшен). Формат
каждого шага: **Действие → Ожидаемый результат** (включая ожидаемые
Telegram-сообщения и клавиатуры).

Покрывает те же 4 сценария, что и `tests/test_e2e_full_flow.py`:

1. Регистрация клиента.
2. Админ: управление клиентами.
3. Записи на приём.
4. Уведомления и напоминания.

---

## 0. Подготовка данных (перед прогоном)

Текущее состояние dev-БД на момент составления чек-листа
(`data/data_base.db`, только для чтения — не изменяйте эти строки
напрямую через SQL, работайте через бота/админ-панель):

| Сущность | Значение |
|---|---|
| Клиника | `id=1`, `name='Зуб Мудрости'`, `token='x7A92JdPkLmQe81'` |
| Админ (со связанной строкой в `users`) | `telegram_user_id=685889801`, `full_name='Мухамеджанов Артём Рустамович'`, `phone='+998999952540'`, `role=admin` |
| Сотрудник без строки в `users` (только `staff`) | `telegram_user_id=226655040` |
| Сотрудник без строки в `users` (только `staff`) | `telegram_user_id=37470594` |
| Тестовый клиент | `id=2`, `telegram_user_id=1494957508`, `full_name='Тестовый Аккаунт'`, `phone='+998946072540'`, `role=client` |
| Таблица `appointments` | **пустая** (0 записей) на момент составления чек-листа |

Важно:

- Таблица записей пуста, поэтому все записи на приём в сценарии 3 и 4
  тестировщик создаёт заново по ходу прогона — отдельной подготовки
  для них не требуется.
- Для входа как администратор используйте Telegram-аккаунт с
  `telegram_user_id=685889801` (единственный сотрудник, у которого уже
  есть привязанная строка в `users` с ролью `admin`). Если нужно
  протестировать вход **другого** сотрудника (`226655040` или
  `37470594`), учтите, что у него ещё нет анкеты в `users` — первое
  обращение к боту должно провести его через сценарий регистрации
  админа (если такой отдельно предусмотрен) либо потребует ручного
  добавления строки в `users`, что выходит за рамки этого чек-листа.
- Для входа как клиент используйте тестовый Telegram-аккаунт с
  `telegram_user_id=1494957508` (уже зарегистрирован, `full_name`
  = «Тестовый Аккаунт», `phone` = `+998946072540`) для сценариев,
  где нужен уже существующий клиент, либо новый незарегистрированный
  Telegram-аккаунт для сценария 1 (регистрация «с нуля»).
- Приглашение в клинику для клиента — токен клиники `x7A92JdPkLmQe81`
  (используется при первом `/start`, если бот запрашивает
  токен/deep-link клиники).

## Сценарий 1. Регистрация клиента

### 1.1. Новый клиент, ранее не встречавшийся в БД

1. **Действие:** С нового (ранее не использовавшегося в этом боте)
   Telegram-аккаунта отправить `/start`.
   **Ожидаемый результат:** Бот приветствует и запрашивает номер
   телефона (кнопка «Отправить номер» / `request_contact`), либо,
   если используется deep-link с токеном клиники, сразу подтверждает
   принадлежность к клинике «Зуб Мудрости».

2. **Действие:** Отправить номер телефона в формате `+998XXXXXXXXX`
   (например, `+998950001122`), которого ещё нет в БД.
   **Ожидаемый результат:** Бот принимает номер и запрашивает ФИО.

3. **Действие:** Отправить корректное ФИО (например, «Расулов Тимур
   Бахтиёрович»).
   **Ожидаемый результат:** Бот подтверждает успешную регистрацию,
   показывает клиентское меню. Пользователь появляется в БД с
   `role=client`, `clinic_id=1`, `telegram_user_id` = ID текущего
   аккаунта.

### 1.2. Повторный `/start` уже зарегистрированным пользователем (идемпотентность)

4. **Действие:** С того же самого аккаунта (уже зарегистрированного на
   шаге 3) снова отправить `/start`.
   **Ожидаемый результат:** Бот **не** запускает регистрацию заново и
   **не** создаёт дублирующую запись клиента — сразу показывает
   клиентское меню/приветствие для уже зарегистрированного
   пользователя. В БД остаётся ровно одна строка с этим
   `telegram_user_id`.

### 1.3. Привязка к уже существующему (созданному админом) пациенту по номеру телефона

5. **Действие:** Через админ-панель (см. сценарий 2, п. 2.1) создать
   клиента с номером `+998950003344` и ФИО «Юсупова Дилноза
   Акмаловна» **без** привязки к Telegram.
   **Ожидаемый результат:** Клиент создан, но не может писать боту
   сам — Telegram-аккаунт ещё не привязан.

6. **Действие:** С нового Telegram-аккаунта отправить `/start` и
   указать номер `+998950003344`.
   **Ожидаемый результат:** Бот находит существующего пациента по
   номеру и предлагает подтвердить/уточнить ФИО «Юсупова Дилноза
   Акмаловна», а не создаёт нового клиента.

7. **Действие:** Подтвердить ФИО (или ввести то же самое ФИО).
   **Ожидаемый результат:** Аккаунт привязывается к существующей
   записи клиента (тот же `id`, что был создан на шаге 5), в БД по
   прежнему одна строка на этого клиента, теперь с заполненным
   `telegram_user_id`.

## Сценарий 2. Админ: управление клиентами

Выполняется от лица администратора (`telegram_user_id=685889801`).

### 2.1. Создание клиента

1. **Действие:** Открыть админ-меню → «Клиенты» → «Добавить клиента».
   **Ожидаемый результат:** Бот запрашивает ФИО, затем телефон.

2. **Действие:** Ввести ФИО «Ахмедов Шерзод Баходирович» и телефон
   `+998933214455`.
   **Ожидаемый результат:** Бот подтверждает создание клиента и
   показывает карточку клиента с указанными данными.

### 2.2. Поиск клиента

3. **Действие:** «Клиенты» → «Поиск» → ввести телефон `+998933214455`.
   **Ожидаемый результат:** Бот находит и показывает карточку клиента
   «Ахмедов Шерзод Баходирович».

4. **Действие:** «Клиенты» → «Поиск» → ввести фамилию «Ахмедов».
   **Ожидаемый результат:** Бот находит того же клиента в списке
   результатов поиска по имени.

### 2.3. Редактирование: телефон

5. **Действие:** Открыть карточку клиента → «Изменить телефон» →
   ввести `+998933214499`.
   **Ожидаемый результат:** Бот подтверждает изменение, карточка
   клиента показывает новый номер.

### 2.4. Редактирование: запрос смены имени (approval workflow)

6. **Действие:** От имени **клиента** (если функциональность доступна
   клиенту) или через соответствующий сценарий запроса смены ФИО,
   отправить запрос на смену имени на «Ахмедов Шерзод Тохирович».
   **Ожидаемый результат:** Администратор (`685889801`) получает
   уведомление вида «✏️ Клиент запросил изменение ФИО» с указанием
   старого и нового ФИО и inline-клавиатурой
   Подтвердить/Отклонить (`name_change_approval.py`).

7. **Действие:** Администратор нажимает «Подтвердить».
   **Ожидаемый результат:** ФИО клиента меняется на «Ахмедов Шерзод
   Тохирович», карточка клиента отражает новое имя.

8. **Действие:** Повторить запрос смены имени на «Ахмедов Отабек
   Шерзодович», администратор нажимает «Отклонить».
   **Ожидаемый результат:** ФИО клиента остаётся «Ахмедов Шерзод
   Тохирович» (без изменений), клиент получает уведомление об отказе
   (если предусмотрено сценарием).

### 2.5. Проверка видимости изменений в client_browser

9. **Действие:** «Клиенты» → «Список клиентов» → пролистать до
   клиента «Ахмедов Шерзод Тохирович».
   **Ожидаемый результат:** В списке отображается актуальное ФИО и
   актуальный телефон (`+998933214499`), то есть все изменения из
   пп. 5–8 видны в общем списке (`client_browser`).

### 2.6. Удаление клиента

10. **Действие:** Открыть карточку клиента «Ахмедов Шерзод Тохирович»
    → «Удалить клиента» → подтвердить.
    **Ожидаемый результат:** Бот подтверждает удаление. Повторный
    поиск по телефону `+998933214499` или по фамилии «Ахмедов» больше
    не находит этого клиента, и он отсутствует в общем списке
    клиентов.

## Сценарий 3. Записи на приём

Выполняется от лица администратора (`685889801`) и клиента
(`1494957508`, «Тестовый Аккаунт»). Даты выбирайте в будущем
относительно даты прогона (минимум на 2–3 дня вперёд), чтобы не
упереться в правило «отмена/перенос не позднее чем за 1 час».

### 3.1. Создание записи администратором

1. **Действие:** Админ-меню → «Записи» → «Создать запись» → указать
   телефон `+998946072540` (существующий тестовый клиент), дату/время
   через 3 дня (например `2026-07-15 10:00`), услугу «Консультация».
   **Ожидаемый результат:** Запись создаётся со статусом «🕐 ожидает»
   (PENDING). Клиент «Тестовый Аккаунт» получает сообщение с деталями
   записи и кнопками подтверждения/отмены
   (`appointment_response_kb`).

2. **Действие:** Клиент нажимает «Подтвердить».
   **Ожидаемый результат:** Статус записи меняется на
   «✅ подтверждена» (CONFIRMED), администратор получает уведомление о
   подтверждении.

### 3.2. Заявка от клиента (self-booking) и решение админа

3. **Действие:** Клиент → «Записаться на приём» → выбрать
   специалиста, дату/время (через 2+ дня), описать жалобу.
   **Ожидаемый результат:** Создаётся заявка со статусом «🕐 ожидает»,
   `created_by=client`. Выбранный специалист получает уведомление
   «🆕 Новая заявка на запись» с кнопками
   Подтвердить/Предложить другое время/Отклонить (`booking_request_kb`).

4. **Действие:** Пока первая заявка клиента не рассмотрена, клиент
   пытается создать вторую заявку на самозапись.
   **Ожидаемый результат:** Бот отказывает («У вас уже есть заявка на
   рассмотрении…») — лимит одновременных заявок = 1.

5. **Действие:** Администратор нажимает «Подтвердить» по заявке из
   п. 3.
   **Ожидаемый результат:** Статус заявки меняется на
   «✅ подтверждена», клиент получает уведомление о подтверждении.

6. **Действие:** Клиент создаёт ещё одну заявку на самозапись (теперь
   лимит свободен) → администратор нажимает «Отклонить».
   **Ожидаемый результат:** Статус заявки — «❌ отменена», клиент
   получает уведомление «Клиника отклонила вашу заявку на запись».

### 3.3. Перенос записи со стороны клиники

7. **Действие:** Открыть подтверждённую запись из п. 2 → «Предложить
   другое время» → указать новую дату/время (через 5 дней).
   **Ожидаемый результат:** Клиент получает сообщение «🔁 Клиника
   предложила другое время…» с кнопками Согласен/Не согласен
   (`reschedule_proposal_kb`).

8. **Действие:** Клиент нажимает «Согласен».
   **Ожидаемый результат:** Дата записи обновляется на предложенную,
   статус остаётся «✅ подтверждена», специалист получает уведомление
   о согласии клиента.

8а. **Действие:** Повторить п. 7 (админ предлагает клиенту новое
    время), но клиент никак не отвечает на сообщение с кнопками
    Согласен/Не подходит.
    **Ожидаемый результат:** За 3 часа до предложенного времени
    клиенту приходит повторное текстовое напоминание (без кнопок) —
    reply на исходное сообщение с предложением и кнопками из п. 7.
    Если клиент всё ещё не отвечает, в момент предложенного времени
    система автоматически отменяет это предложение — запись остаётся
    подтверждённой (✅) на её ИСХОДНОЕ время. Предложение о переносе
    просто стирается, статус записи не меняется.

### 3.4. Перенос записи со стороны клиента

9. **Действие:** Клиент открывает ту же подтверждённую запись →
   «Перенести запись» → указывает новую дату/время (через 6 дней,
   более чем за 1 час от текущего момента).
   **Ожидаемый результат:** Администратор получает уведомление
   «🔁 Клиент просит перенести запись» с кнопками Принять/Отклонить
   (`reschedule_request_kb`).

10. **Действие:** Администратор нажимает «Принять».
    **Ожидаемый результат:** Дата записи обновляется на предложенную
    клиентом, запись остаётся «✅ подтверждена».

### 3.5. Отмена записи

11. **Действие:** Клиент открывает запись (дата — не позднее чем за 1
    час до приёма) → «Отменить запись» → подтвердить.
    **Ожидаемый результат:** Статус записи — «❌ отменена».
    Администратор получает уведомление об отмене клиентом.

### 3.6. Завершение приёма (completion follow-up)

12. **Действие:** Создать новую подтверждённую запись с временем в
    ближайшем прошлом/настоящем (для теста можно использовать запись,
    время которой уже наступило +1 час, либо дождаться реального
    времени приёма +1 час).
    **Ожидаемый результат:** Через 1 час после времени приёма
    администратор получает сообщение «Приём завершён. Внести
    исправления?» с кнопками Да/Нет (`completion_followup_kb`).
    Статус записи **не** меняется автоматически — остаётся
    «✅ подтверждена».

13. **Действие:** Администратор нажимает «Нет».
    **Ожидаемый результат:** Статус записи становится
    «✔️ завершена» (COMPLETED). Сообщение редактируется на «Приём
    завершён.» с кнопкой «Подробнее».

14. **Действие (альтернативная ветка):** На шаге 12 администратор
    вместо «Нет» нажимает «Да».
    **Ожидаемый результат:** Сначала запись завершается
    («✔️ завершена» / COMPLETED), затем открывается карточка записи в
    режиме пост-приёмного редактирования; доступна кнопка «Завершить
    приём».

### 3.7. Проверка пагинации по вкладкам

15. **Действие:** Админ-меню → «Записи» → «Список всех записей» →
    открыть вкладку «🕐 Ожидание».
    **Ожидаемый результат:** В списке видны только записи со статусом
    PENDING (например, необработанные заявки из п. 3.2, если такие
    остались).

16. **Действие:** Переключиться на вкладку «✅ Подтверждённые».
    **Ожидаемый результат:** В списке видны только записи со статусом
    CONFIRMED; ранее завершённая запись из п. 13 в этой вкладке
    отсутствует и отображается во вкладке «Завершённые».

### 3.8. Сброс FSM после успешного завершения приёма

17. **Действие:** Перейти в поиск записи по ФИ и дойти до шага, где бот показывает `Введите ФИ:`.
    **Ожидаемый результат:** Поиск по ФИ активен, бот ждёт ввод имени.

18. **Действие:** Не вводя ФИ, нажать в follow-up по завершению приёма кнопку `Нет, всё верно`.
    **Ожидаемый результат:** Follow-up редактируется в `Приём завершён.` с кнопкой `Подробнее`.

19. **Действие:** Отправить валидное полное имя.
    **Ожидаемый результат:** Бот не продолжает старый поиск приёма и не возвращает прежний шаг ввода ФИ.

20. **Действие:** Нажать `Подробнее`.
    **Ожидаемый результат:** Открывается полная карточка завершённого приёма; затем нажать `Скрыть` и убедиться, что снова показывается компактное сообщение `Приём завершён.`.

21. **Действие:** Повторить сценарий, но на follow-up нажать `Да, завершить`.
    **Ожидаемый результат:** Открывается полная пост-приёмная карточка, а старый поиск по имени не возобновляется.

22. **Действие:** После завершения сценария снова отправить валидное имя, которое использовалось на шаге 17.
    **Ожидаемый результат:** Бот ведёт себя как после обычного сообщения в чате, без возврата к старому FSM-состоянию ввода ФИ.

## Сценарий 4. Уведомления и напоминания

1. **Действие:** Создать (или использовать) подтверждённую запись с
    датой через 2+ дня, дождаться (либо сократить окружение
    dev/staging для ускоренной проверки) момента ровно за 24 часа до
    приёма.
    **Ожидаемый результат:** Клиент получает короткое сообщение
    «Напоминаем вам о записи.» **без** кнопок подтверждения (реплай на
    исходное сообщение о записи), администратор получает сообщение
    «📌 Предстоящая запись: …» с данными клиента.

2. **Действие:** Дождаться момента ровно за 2 часа до приёма.
    **Ожидаемый результат:** Клиент получает такое же напоминание, но
    **с** кнопками подтверждения/отмены; администратор снова получает
    «📌 Предстоящая запись: …».

3. **Действие:** Через 1 час после времени приёма (см. также
    сценарий 3.6).
    **Ожидаемый результат:** Администратору приходит follow-up
    «Приём завершён. Внести исправления?» — см. пп. 12–14.

4. **Действие:** Отменить (или удалить) запись **до** наступления
    времени одного из запланированных напоминаний (например, сразу
    после создания).
    **Ожидаемый результат:** Ни клиент, ни администратор **не**
    получают напоминания 24ч/2ч и follow-up о завершении по этой
    записи — соответствующие задачи планировщика были отменены вместе
    с отменой записи.

## Сценарий 5. Автогенерация истории болезни при завершении записи

Выполняется от лица администратора (`685889801`) и клиента
(`1494957508`, «Тестовый Аккаунт`). Тестирует генерацию `.docx` через Ollama
при завершении записи (любым из трёх путей) и получение файла обеими
сторонами через кнопку.

### 5.1. Завершение записи и генерация документа (path: админ "изменить" на T+1ч)

1. **Действие:** Создать новую подтверждённую запись с временем в ближайшем
   прошлом (например, 1 час назад). Диагноз указать со слова, позволяющим
   отследить зуб, например «Кариес 37 зуба» (или любой другой номер зуба
   от 11 до 48).
   **Ожидаемый результат:** Запись создана и подтверждена (статус
   «✅ подтверждена»).

2. **Действие:** Дождаться момента ровно T+1ч (1 час после времени приёма),
   когда администратор получит сообщение follow-up «Приём завершён. Внести
   исправления?» с кнопками «Да» и «Нет».
   **Ожидаемый результат:** Сообщение пришло администратору.

3. **Действие:** Администратор нажимает «Нет» (завершает приём без редактирования).
   **Ожидаемый результат:** Статус записи становится «✔️ завершена» (COMPLETED).
   В фоне начинается генерация медкарты (на этом этапе может ещё не быть
   готова). Сообщение редактируется на «Приём завершён.» без кнопок.

### 5.2. Завершение записи и генерация документа (path: админ "пропустить" на T+1ч)

4. **Действие:** Создать новую подтверждённую запись с временем в ближайшем
   прошлом. Диагноз указать со слова для отслеживания зуба, например
   «Пульпит 45 зуба».
   **Ожидаемый результат:** Запись создана и подтверждена.

5. **Действие:** Дождаться момента ровно T+1ч, получить follow-up
   «Приём завершён. Внести исправления?».
   **Ожидаемый результат:** Сообщение пришло администратору.

6. **Действие:** Администратор нажимает «Да» (открывает карточку в режиме
   редактирования), затем нажимает «Завершить приём» или использует кнопку
   пропуска редактирования (если предусмотрено).
   **Ожидаемый результат:** Статус записи становится «✔️ завершена» (COMPLETED).
   Генерация медкарты начинается в фоне.

### 5.3. Завершение записи и генерация документа (path: автокомплит на T+2ч или past-due)

7. **Действие:** Создать новую подтверждённую запись с временем более 2 часов
   в прошлом. Диагноз указать со слова для отслеживания зуба, например
   «Консультация + удаление 28 зуба».
   **Ожидаемый результат:** Запись создана и подтверждена.

8. **Действие:** Дождаться момента ровно T+2ч (2 часа после времени приёма)
   или дождаться рестарта планировщика (если время прошло) — автокомплит
   должен сработать.
   **Ожидаемый результат:** Статус записи становится «✔️ завершена» (COMPLETED),
   администратор может получить уведомление об автокомплите (если предусмотрено).
   Генерация медкарты начинается в фоне.

### 5.4. Получение готового документа через кнопку (администратор)

9. **Действие:** Открыть карточку завершённой записи из п. 3, 6 или 8
   (любой из путей завершения) → найти кнопку «📄 Получить историю болезни».
   **Ожидаемый результат:** Кнопка видна в завершённой записи (рядом с
   информацией о сроках и статусе).

10. **Действие:** Нажать кнопку «📄 Получить историю болезни» **сразу после**
    завершения записи (пока генерация может быть ещё в процессе, если прошло
    менее 5 секунд).
    **Ожидаемый результат:** Бот показывает alert:
    «Документ ещё готовится, попробуйте через пару минут» (если генерация ещё
    идёт) или отправляет файл медкарты (если уже готов, что возможно на
    быстрых машинах).

11. **Действие:** Подождать несколько секунд (обычно 10–30 секунд в зависимости
    от Ollama) и повторить попытку получения документа через кнопку.
    **Ожидаемый результат:** Бот отправляет файл `medical_card_{appointment_id}.docx`
    в чат администратора. Файл можно скачать и открыть в MS Word / LibreOffice.

### 5.5. Получение готового документа через кнопку (клиент)

12. **Действие:** От имени клиента (`1494957508`, «Тестовый Аккаунт`) открыть
    список своих записей / историю → найти ту же завершённую запись из п. 3,
    6 или 8 в карточке истории.
    **Ожидаемый результат:** В карточке завершённой записи видна кнопка
    «📄 Получить историю болезни».

13. **Действие:** Клиент нажимает кнопку «📄 Получить историю болезни»
    (гарантированно после того, как администратор уже получил документ, т.е.
    документ точно готов).
    **Ожидаемый результат:** Клиент получает тот же файл медкарты в своём чате.

### 5.6. Проверка корректности полей документа

14. **Действие:** Открыть полученный `.docx`-файл в MS Word / LibreOffice.
    **Ожидаемый результат:** Документ открывается без ошибок и содержит заполненные
    плейсхолдеры:
    - `{{ appointment_date }}` — дата и время приёма из записи (например,
      «2026-07-15 14:30»);
    - `{{ full_name }}` — ФИО клиента (например, «Тестовый Аккаунт»);
    - `{{ gender }}` — пол клиента («Мужской» или «Женский»);
    - `{{ birth_date }}` — дата рождения клиента (если указана в БД);
    - `{{ phone }}` — телефон клиента;
    - `{{ diagnosis }}` — исходный диагноз / описание услуги, введённый админом
      (например, «Кариес 37 зуба»);
    - `{{ complaints }}`, `{{ diseases }}`, `{{ examination }}`, `{{ treatment }}` —
      заполнены Ollama (если была доступна и успешна) или пустые строки
      (если Ollama сбойнула или недоступна).

### 5.7. Проверка отметки зуба на карте

15. **Действие:** На той же открытой странице документа найти таблицу с зубной
    картой (обычно это вторая таблица в шаблоне).
    **Ожидаемый результат:** На зубной карте (в сетке с номерами зубов 11–48)
    в ячейке, соответствующей указанному в диагнозе зубу, виден маркер
    (например, «C» для кариеса, «P» для пульпита, «X» для удаления и т.д.),
    выделенный полужирным шрифтом, центрирован в ячейке.

    Примеры проверки маркеров:
    - Диагноз «Кариес 37 зуба» → маркер «C» в ячейке зуба 37.
    - Диагноз «Пульпит 45 зуба» → маркер «P» в ячейке зуба 45.
    - Диагноз «Удаление 28 зуба» → маркер «X» в ячейке зуба 28.

## Миграции

### `users.created_at`: таймзона

Новые клиенты (регистрация, создание админом, fallback-создание при
записи на приём) получают `created_at` в Asia/Tashkent (UTC+5),
записанное явно из Python — как и `appointments.created_at`.
Исторические строки, созданные до фикса, были в UTC (SQL-дефолт
`CURRENT_TIMESTAMP`) и сдвигаются один раз скриптом
`scripts/migrate_users_created_at_timezone.py`. Скрипт запускается
**один раз** перед деплоем на staging/prod и **не идемпотентен** —
повторный запуск сдвинет даты ещё на 5 часов. Не запускать его
повторно на уже мигрированной БД.

### Перед деплоем: проверка, что миграция `users.created_at` не задела job store планировщика

Миграция работает напрямую с SQLite-таблицей `users` через `sqlite3` и
физически не пересекается с job store `AsyncIOScheduler` (задачи
напоминаний/авто-истечения записей), но перед деплоем на staging/prod
рекомендуется явно в этом убедиться:

1. Перед прогоном скрипта снять список активных задач планировщика:
   `scheduler.get_jobs()` (зафиксировать `id` и `next_run_time` каждой
   задачи).
2. Прогнать `python scripts/migrate_users_created_at_timezone.py`.
3. Снова снять `scheduler.get_jobs()` и сравнить со снимком из шага 1 —
   списки должны быть идентичны (тот же набор `id`, те же
   `next_run_time`, ничего не потеряно и не задвоено).
4. Если бот перезапускается между шагами 1 и 3 (например, в рамках
   деплоя) — сравнение можно провести после первого прогона планировщика
   после рестарта, вместо сравнения "живого" состояния до/после.

Автоматическая регрессия на этот сценарий — тест
`test_users_created_at_migration_does_not_disturb_scheduled_jobs` в
`tests/test_appointment_scheduler.py`.
